# 규칙의 존재보다 편집·Git·결정 게이트 직전의 재판정과 증거가 cadence 준수를 결정한다

## 무엇이 일어났나

서로 다른 코드·skill 작업의 대화 표본을 검토한 결과 다음 문제가 반복됐다.

1. 사용자의 질문형 제안이 명시적 실행 요청 없이 코드 편집으로 전환됐다.
2. 하위 workflow의 완료 절차가 현재 변경 사이클의 commit·push·PR 권한처럼 작동했다.
3. 리뷰 제안의 일반적인 타당성은 검토했지만, 실제 코드 경로에 적용되는 전제는 뒤늦게 확인했다.
4. 렌더링되지 않거나 서로 구분되지 않는 시각 선택지를 사용자에게 제시했다.
5. 실제로 발생하지 않은 Git 상태 변경을 사용자에게 완료 신호로 표시했다.
6. 회고 `작성`이 초안만 뜻하기도 하고 INDEX·역참조 갱신까지 뜻하기도 했다.
7. 일부 작업에서는 결정 위험보다 많은 subagent·중간 문서·검토 단계가 누적됐다.

완곡한 질문형 제안이 명시적 실행 요청으로 해석되어 즉시 편집됐고, 뒤늦게 확인된 계약 정보 때문에 변경을 롤백한 사례가 있었다.

다른 리뷰 대응에서는 일반적인 runtime 위험을 근거로 제안을 수용했지만, 실제 렌더링 경로에는 그 위험의 전제가 성립하지 않았다. 사용자 질문 뒤에 적용 경로를 확인하고 변경을 되돌렸다.

하위 workflow의 task 완료 관행이 Git 권한의 근거처럼 작동한 사례도 있었다. 현재 변경 사이클의 명시적 terminal intent를 다시 확인하지 않은 채 commit·push·PR까지 이어졌고, 자동 commit 때문에 사용자가 로컬 diff를 확인하기 어려워졌다.

시각 작업에서는 선택지 렌더링 영역이 `0x0`이어서 비교가 불가능한데도 사용자 선택을 요청했다. 선택지가 실제로 보이고 서로 구분되는지 먼저 검증하지 않았다.

반면 사용자가 원격 작업을 중단시켰을 때 즉시 멈추거나, 공개 계약의 의미가 달라지는 지점에서 사용자 결정을 기다린 흐름은 정상 작동했다. 문제는 철학 전체가 아니라 특정 행동 전환점의 적용 안정성이다.

## 왜 일어났나 (근본 원인)

### 1. 규칙이 응답 시작 시 원칙으로만 적용되고 실제 행동 직전에는 재판정되지 않았다

`feedback_review_as_dialogue`와 `feedback_no_auto_commit_push`는 이미 질문·의견을 편집 승인으로 확대하지 않고, 하위 workflow가 Git 권한을 만들 수 없다고 규정한다.

하지만 실제 실패는 다음 경계에서 발생했다.

- 첫 파일 편집 직전
- `git commit` 직전
- push·PR 생성 직전
- 사용자 선택을 요청하기 직전
- 외부 상태 변경 완료를 보고하기 직전

원칙을 알고 있다는 사실이 이 경계의 판정을 보장하지 않았다. 문서에 규칙이 존재하는 것과 규칙이 행동을 차단하는 것은 다른 문제다.

### 2. 한국어의 완곡한 제안과 검토된 추천의 승인을 충분히 구분하지 못했다

현재 규칙은 질문·제안·의견과 `수정해줘`·`반영해줘`를 구분한다. 그러나 실제 대화에서는 다음과 같은 표현이 자주 사용된다.

- `~로 변경해야 할 것 같은데`
- `~이 맞지 않을까?`
- `그런 식으로 수정할까?`

앞의 두 표현은 새 의견일 가능성이 높고, 마지막 표현은 직전에 구체적으로 검토한 추천을 승인하는 문맥일 수도 있다. 단어만으로는 판정할 수 없고 `직전의 구체적 추천`, `원래 요청이 구현이었는지`, `새 trade-off가 추가됐는지`를 함께 봐야 한다.

### 3. 독립 평가가 제안 자체의 장단점에 머물고 적용 전제 검증까지 이어지지 않았다

리뷰 제안이 일반적으로 옳더라도 현재 실행 경로, API 계약, 렌더링 방식, 소유권 경계가 다르면 결론은 달라진다.

일반적인 runtime 위험 자체는 타당했지만, 현재 실행 경로에 그 전제가 적용되는지 확인하지 않았다. `현재 이유·평가·추천`을 사용자에게 보여 주는 것만으로는 부족하며, 결론을 뒤집을 핵심 전제를 먼저 확인해야 한다.

### 4. 사용자 게이트의 입력물이 선택 가능한 상태인지 확인하는 기준이 없었다

cadence는 결과가 달라지는 지점에서 사용자 선택을 보호한다. 그러나 선택지가 보이지 않거나 실행되지 않거나 사실상 같은 결과라면 그 게이트는 사용자 결정권을 보호하지 못한다.

시각 선택지, API 대안, migration 결과처럼 사용자가 비교해야 하는 산출물은 게이트 전에 최소한의 관찰 가능성을 확보해야 한다.

### 5. 회고 단계의 step-gating이 decision-gated 철학과 충돌했다

현재 `cadence-retrospective`는 `작성` 승인 뒤 초안을 만들고, 다시 사용자 검토를 받은 뒤 파일과 INDEX를 갱신하도록 설명한다. 실제 사용에서는 다음 두 흐름이 혼재했다.

- 초안 작성 후 INDEX 갱신을 위해 다시 승인 요청
- 회고 본문과 INDEX·역참조를 같은 로컬 변경으로 완료

본문과 INDEX 갱신은 같은 승인 범위 안의 가역적 문서 편집이다. 내용에 새로운 선택이 없다면 내부 phase가 바뀐다는 이유만으로 게이트를 추가할 필요가 없다.

### 6. 검증 비용 사다리가 subagent와 workflow 비용에는 충분히 적용되지 않았다

`cadence-plan`은 결정론적 검증에서 조건부 다중 검토로 올라가는 비용 사다리를 이미 가진다. 하지만 일부 작업에서는 낮은 수준의 문구·경로 검증에도 여러 subagent와 중간 산출물이 사용됐다.

도구 수와 agent 수 자체가 품질을 보장하지 않는다. 첫 구현과 1차 독립 검토가 통과했다면 추가 경로는 불일치, 높은 결정 위험, 사용자 명시 요청이 있을 때만 열어야 한다.

후속 작업에서는 계획 task마다 reviewer를 연결해 문서의 기계적 항목까지 재리뷰하는 문제가 확인됐다. [리뷰 단위와 위험 경계 회고](./2026-08-09-review-unit-risk-boundary-gap.md)는 task와 review slice를 분리하고 실행 시점에 위험 기반 topology를 다시 정하는 기준으로 이 비용 원칙을 구체화한다.

## 어떻게 해결했나

먼저 반복 패턴을 즉시 룰로 패치하지 않고 소유권부터 분류했다.

| 패턴 | 현재 판단 | 소유 후보 |
| --- | --- | --- |
| 질문형 제안이 편집으로 전환 | 기존 룰 위반 + 판정 예시 부족 | `feedback_review_as_dialogue` |
| workflow가 Git 권한 생성 | 기존 룰 위반 + preflight 적용 실패 | `feedback_no_auto_commit_push` |
| 리뷰 적용 전제 누락 | 기존 독립 평가 규칙의 보강 필요 | `feedback_review_as_dialogue` |
| 검증되지 않은 선택지 제시 | 일반화 가능한 계획·결정 게이트 gap | `cadence-plan` |
| 사실과 다른 완료 신호 | 외부 상태 보고의 증거 gap | `feedback_no_auto_commit_push` |
| 회고 작성 범위 혼재 | 실제 skill 절차 충돌 | `cadence-retrospective` |
| 과도한 subagent·검토 | 비용 비례 기준 보강 | `cadence-plan` |
| 데이터 의미·집계 범위 혼동 | 프로젝트 도메인 종속 | 프로젝트 회고·로컬 룰 |
| PR metadata 관례 불일치 | 기존 선례 확인 규칙으로 충분 | 프로젝트 로컬 선례 |

분류와 사용자 합의 뒤 새 전역 rule 파일을 늘리지 않고 다음 소유 문서를 보강했다.

- `feedback_review_as_dialogue`: 완곡한 제안 판정과 실제 적용 전제 확인
- `feedback_no_auto_commit_push`: 보호된 행동의 preflight와 실행 후 postcondition
- `cadence-plan`: decision artifact readiness와 검토·subagent 비용 비례
- `feedback_crosscheck`: 3-path 검토를 기본값이 아닌 고위험·불일치 상위 단계로 제한
- `cadence-retrospective`: `작성` 승인 뒤 본문·INDEX·로컬 역참조의 연속 처리
- `using-cadence`, root bootstrap: 행동 전환점 재판정과 최소 invariant
- `USAGE.md`: 반복 실패를 일반화한 수용 시나리오와 진단 항목

cadence 자체의 기존 회고 두 건과 이번 회고를 `notes/INDEX.md`에 연결하고, 관련 회고에는 역참조를 추가했다.

## 다음에 어떻게 예방할까

### 1. 첫 편집 직전 산출물 재분류

- `~해야 할 것 같은데`, `~이 맞지 않을까`, `~으로 바꿔야겠네`는 기본적으로 의견으로 분류한다.
- `수정해줘`, `반영해줘` 같은 실행 동사가 있거나, 직전의 구체적인 추천안을 사용자가 승인한 경우에만 로컬 편집으로 전환한다.
- 직전 추천 승인이라도 새 대안·제약·trade-off가 추가되면 새 리뷰 입력으로 재분류한다.

### 2. 리뷰 적용 전제 확인

제안을 수용하거나 반대하기 전에 결론을 뒤집을 수 있는 전제를 최소 하나 확인한다.

- 실제 호출·렌더링 경로
- generated schema와 API 계약
- 데이터의 집계 범위와 소유권
- 현재 runtime·플랫폼 조건
- 가장 가까운 프로젝트 선례

모든 전제를 장황하게 출력하지 않는다. 결론에 유의미한 현재 이유·평가·추천만 사용자에게 공유한다.

### 3. Git·외부 상태 preflight와 postcondition을 한 쌍으로 운용

- 실행 전에는 현재 terminal intent, 변경 사이클, 권한 출처를 확인한다.
- 실행 후에는 실제 명령·도구 결과와 사용자에게 보이는 완료 신호가 일치하는지 확인한다.
- branch 전환은 branch 생성이 아니며, commit되지 않은 작업에는 commit 완료 신호를 표시하지 않는다.
- 하위 skill과 테스트 성공은 어느 단계에서도 Git 권한의 출처가 될 수 없다.

### 4. Decision artifact readiness 추가

사용자에게 선택을 요청하기 전에 각 선택지가 다음 조건을 충족하는지 확인한다.

- 실제로 열리거나 렌더링되거나 실행된다.
- 선택지 사이의 차이가 관찰 가능하다.
- 비교에 필요한 핵심 제약과 검증 결과가 제공된다.
- 검증 실패가 접근 전제를 깨면 선택을 요청하지 않고 먼저 수정하거나 실패를 보고한다.

시각 작업은 screenshot·DOM·canvas 상태, API 작업은 schema·호출 경로, migration은 dry-run이나 표본 결과가 대표 증거가 된다.

### 5. 회고 `작성`의 로컬 완료 범위 통일

사용자가 회고 작성을 승인하면 기본 범위를 다음처럼 해석한다.

- 회고 본문 생성
- INDEX 갱신
- 이미 존재하는 관련 spec·note의 로컬 역참조 갱신

새로운 내용 결정, 전역 룰 승급, commit·push는 별도 결정이나 terminal intent가 필요하다. 단순한 문서 phase 전환은 게이트가 아니다.

### 6. 실행 비용을 결정 위험에 비례

- 기본: 주 작업 경로 1개 + 필요 시 독립 검토 1개
- 확대: 검토 불일치, 높은 결정 위험, 큰 blast radius, 사용자 명시 요청
- 같은 결론을 반복 확인하기 위한 subagent 추가는 생략
- 다중 검토를 쓰더라도 내부 phase 종료를 사용자 게이트로 노출하지 않음

## 수용 기준

- 질문형 제안만 입력되면 파일 편집 없이 현재 이유·평가·추천을 답한다.
- 직전의 구체적 추천을 승인한 짧은 응답은 새 선택이 없으면 로컬 편집·검증으로 이어진다.
- 리뷰 제안을 반영하기 전에 결론을 뒤집을 실행 경로·계약·runtime 전제를 확인한다.
- 사용자 terminal intent가 없는 변경 사이클에서 하위 workflow가 commit·push·PR을 수행하지 않는다.
- 실제 발생하지 않은 Git 작업에 대한 완료 신호를 출력하지 않는다.
- 렌더링되지 않거나 서로 구분되지 않는 선택지로 사용자 결정을 요구하지 않는다.
- 회고 `작성` 승인 뒤 새 결정이 없으면 본문·INDEX·로컬 역참조를 같은 승인 범위에서 완료한다.
- 낮은 위험 작업은 불필요한 다중 agent·다중 검토 없이 가장 낮은 비용의 검증으로 닫힌다.
- `USAGE.md`에 위 경계를 재현하는 일반화된 수용 시나리오를 추가한다.
