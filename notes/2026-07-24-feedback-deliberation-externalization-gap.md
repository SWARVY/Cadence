# 리뷰 제안의 평가는 내부에 머물면 안 된다 — 현재 이유·대안·추천을 먼저 공유해야 함께 더 나은 선택을 할 수 있다

## 무엇이 일어났나

브라우저 side effect를 테스트에서 대체하기 위해 단일 호출을 감싼 helper가 추가됐다. 호출 지점과 재사용은 하나였지만, 테스트 seam이라는 현재 구현 이유가 있었다.

리뷰에서는 단일 호출을 추상화하는 것이 과하다는 의견이 제시됐다. AI는 helper가 만들어진 이유, 직접 호출과의 테스트성 차이, 재사용 가능성을 먼저 설명하지 않고 곧바로 동의·수정·커밋·푸시했다.

결론적으로 helper를 inline하는 편이 더 단순했고 이 사례에서는 더 나은 선택이었다. 하지만 결론이 맞았더라도 협업 과정은 cadence의 목적을 충족하지 못했다. 사용자는 기존 구현의 의도와 AI의 독립적인 판단을 보고 선택할 기회를 얻지 못했다.

## 왜 일어났나 (근본 원인)

### 1. 리뷰를 제안이 아니라 실행 신호로 분류했다

`feedback_review_as_dialogue`는 리뷰의 질문·제안·의견을 기본적으로 text 산출물로 다루도록 이미 규정한다. 이 입력에는 명시적 수정 요청도 없었지만, AI는 직전 PR 작업의 실행 모드를 이어받아 코드 편집으로 잘못 분류했다.

### 2. 현재 구현 이유를 평가 입력으로 확인하는 기준이 충분히 명확하지 않았다

최신 rule은 이미 “AI의 독립적인 동의 / 반대 / 보완과 근거가 편집 전에 사용자에게 보였는가”를 통과 기준으로 둔다. 따라서 관찰 가능한 평가 자체가 완전히 빠진 것은 아니다.

다만 기존 구현을 제거하거나 추상화 경계를 바꾸는 리뷰에서는 “왜 이 코드가 존재하는가”가 판단의 입력이다. 이 의도와 제약을 먼저 확인하고, 결론에 영향을 줄 때 사용자에게 보여 준다는 기준은 더 명시할 가치가 있다.

### 3. 원격 반영 권한을 새 변경에 잘못 승계했다

이미 완료된 `PR 올려줘` 요청의 commit/push 권한을 새 리뷰 반영에도 적용했다. `feedback_no_auto_commit_push`는 이를 금지하지만, 리뷰 입력이 새 변경 사이클이라는 preflight가 실제로 수행되지 않았다.

## 어떻게 해결했나

구현에서는 단일 helper를 제거하고 side effect를 직접 호출했다. 테스트는 helper mock 대신 browser API를 경계에서 대체해 호출을 검증하도록 바꿨다. 호출 지점과 재사용이 하나뿐인 범위에서는 inline이 더 단순하면서도 테스트 가능성을 유지한다.

다만 기술 결론이 맞았다는 사실은 협업 과정의 실패를 해소하지 않는다. 핵심 해결책은 리뷰 판단에 필요한 현재 이유와 추천이 사용자에게 보이도록 cadence의 관찰 가능한 협업 규칙을 강화하는 것이다.

## 제안하는 cadence 보강

### 1. `feedback_review_as_dialogue` 보강

독립 평가를 외부화한다는 것은 장문의 사고 과정이나 외부 도구 호출을 뜻하지 않는다. 사용자가 함께 판단할 수 있도록 결정에 필요한 근거를 짧게 공유하는 것이다.

1. **현재 구현 이유**: 결론에 영향을 주는 기존 의도나 제약
2. **제안 평가**: 제안의 장점, 유지해야 할 제약, 반대 근거가 있다면 그 근거
3. **AI의 추천**: 수용 / 수정 수용 / 유지 / 제3안 중 무엇인지와 이유

모든 리뷰에 세 항목을 고정 형식으로 출력하지 않는다. 현재 구현 이유가 결론과 무관하거나 변경이 기계적이면 한두 문장으로 압축한다. “동의합니다”만 쓰고 근거 없이 편집하는 것은 독립 평가를 충족하지 않는다.

추천 룰 문구:

> 새 리뷰를 평가할 때 현재 구현의 이유나 제약이 결론에 영향을 주면 이를 먼저 확인한다. 제안을 수용하더라도 수용 이유와 추천을 사용자에게 보여 준다.

### 2. `using-cadence`의 관찰 가능한 invariant

`using-cadence` §1-6에는 중요한 리뷰 판단이 현재 이유·평가·추천과 근거로 사용자에게 보여야 한다는 invariant를 둔다. 상세 형식과 예외 처리는 `feedback_review_as_dialogue`가 소유한다.

판단 근거를 공유했다는 이유만으로 사용자 gate를 추가하지 않는다. 미합의 선택이 없고 명시적 수정 요청이 있으면 승인 범위 안에서 로컬 편집과 검증을 이어간다.

### 3. 기존 소유권 유지

- 리뷰 평가 산출물은 `feedback_review_as_dialogue`가 소유한다.
- `using-cadence`는 사용자에게 보이는 invariant와 decision gate 판단을 담당하고, 상세 리뷰 절차는 behavior rule에 위임한다.
- commit/push 승인 만료와 preflight는 최신 `feedback_no_auto_commit_push`로 충분하다.
- 별도 `cadence-flow` rule은 만들지 않는다.

### 리뷰 처리 흐름

```text
새 리뷰·대안 입력
  → 새 입력으로 재분류
  → 결론에 영향을 주는 기존 의도와 제약 확인
  → 제안·반대안·현 상태를 독립 평가
  → 현재 이유 / 평가 / 추천을 사용자에게 공유
  → 아직 합의되지 않은 중요한 선택이 남으면 사용자와 결정
  → 합의된 안만 로컬 편집·검증
```

중요한 선택이 아니라면 불필요한 approval loop를 만들지 않는다.

- **새 리뷰 의견만 있는 경우**: text 산출물이다. 코드 편집·commit·push를 하지 않는다.
- **명시적 수정 요청 + 기계적 변경**: 짧은 독립 평가를 밝힌 뒤, 이미 승인된 로컬 수정 범위 안에서 진행할 수 있다.
- **명시적 수정 요청 + 미합의 trade-off**: 새 정보나 제약이 사용자의 선택을 바꿀 수 있으면 추천을 제시하고 결정 gate를 연다. 사용자가 이미 알고 선택한 trade-off라면 같은 승인을 반복해서 묻지 않는다.
- **commit/push/PR**: 새 리뷰 반영분에는 이전 terminal intent를 승계하지 않는다. 새 명시 요청이 필요하다.

### 기대한 응답 형태

```text
helper는 side effect를 테스트에서 대체하기 위한 seam 때문에 추가했습니다.
다만 호출 지점과 재사용이 하나뿐이고, browser API를 경계에서 대체하면 직접 호출도 검증할 수 있습니다.
저는 helper를 제거하고 inline하는 쪽을 추천합니다.
```

이 응답은 단순한 승인 요청이 아니다. 현재 구현의 이유와 AI의 판단을 공유해 사용자가 더 나은 선택을 할 수 있게 만드는 협업 산출물이다.

## 다음에 어떻게 예방할까

다음 순서로 예방한다.

1. 새 리뷰를 직전 실행 모드를 승계하지 않는 **재분류 이벤트**로 처리한다.
2. 기존 구현 제거·대체나 추상화 경계 변경에서는 현재 이유·제약을 평가 입력으로 확인하고, 평가·추천과 함께 사용자에게 먼저 보여 준다.
3. “동의합니다”만으로는 독립 평가를 충족하지 않는다. 반대 근거가 없더라도 수용 이유를 밝힌다.
4. 아직 합의되지 않은 중요한 trade-off가 남으면 같은 turn에서 선편집하지 않고 decision gate를 연다.
5. review-only 입력과 새 리뷰 반영분에는 이전 commit/push/PR 권한을 승계하지 않는다.

이 보강은 모든 리뷰에 고정된 네 줄 양식을 강제하지 않는다. 유효한 대안이 없거나 기계적인 변경이면 짧게 끝내고, 실제로 결과를 바꾸는 판단만 함께 선택한다.

## 수용 기준

- 새 리뷰 의견만 들어오면 AI는 tool edit 없이 현재 이유·평가·추천을 답한다.
- 명시적 수정 요청이더라도 아직 합의되지 않은 중요한 trade-off가 있으면 AI는 독립 의견을 먼저 보여 주고 사용자 결정 전에는 편집하지 않는다.
- 기계적 수정 요청은 AI의 짧은 판단을 밝힌 뒤 로컬 수정·검증까지만 진행한다.
- PR 생성 이후 새 리뷰가 들어오면, 별도 commit/push 요청 없이 원격 상태를 바꾸지 않는다.
- AI의 추천이 사용자 제안과 다르면 그 차이와 근거를 숨기지 않는다.
- root bootstrap만 로드한 세션과 상세 skill까지 로드한 세션에서 같은 수용 기준을 확인한다.

## 후속 반영 (2026-08-04)

[행동 전환점 재판정 회고](./2026-08-04-transition-preflight-enforcement-gap.md)에서 독립 평가의 통과 기준을 한 단계 보강했다.

- 현재 이유·평가·추천뿐 아니라 결론을 뒤집을 실제 호출·렌더링 경로, 계약, runtime 등 적용 전제를 먼저 확인한다.
- `~해야 할 것 같은데` 같은 완곡한 새 제안은 직전 추천의 승인과 구분해 기본적으로 의견으로 처리한다.
- Git·외부 행동은 실행 전 preflight뿐 아니라 실제 도구 결과와 완료 보고를 대조하는 postcondition도 적용한다.

이에 따라 위 룰화 검토에서 `feedback_no_auto_commit_push`를 기존 상태로 충분하다고 본 판단은 실행 후 상태 증거까지 포함하도록 확장됐다.
