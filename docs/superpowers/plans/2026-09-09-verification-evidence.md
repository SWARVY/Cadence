# 수용 시나리오와 검증 증거 개선 계획

**목표:** AI가 구현 전에 기대 동작을 구체화하고, 그 동작을 실제로 확인할 수 있는 검증을 선택하며, 확인한 범위만 완료로 보고하게 한다.

**설계:** 기존 `cadence-plan`의 검증 책임을 확장한다. 핵심 원칙은 진입 문서에, 시나리오·테스트 유지보수·실패 기록의 상세 예시는 `references/verification.md`에 둔다. `using-cadence`는 진입 시점과 사용자 결정 경계를 연결한다.

**형식:** Markdown skill과 문서. 새로운 런타임이나 테스트 프레임워크 의존성을 추가하지 않는다.

## 근거와 선택

- 현재 §4는 추가 AI 리뷰의 비용 사다리에 집중한다. 동작에 필요한 검증 수단은 추가 리뷰 여부와 별개로 정해야 한다.
- 기존 spec 메타 구조는 검증 결과를 매핑하지만 실제 템플릿에는 해당 섹션이 없다.
- 테스트 전략 전체를 새 skill로 분리하는 대안은 라우팅·승인 규칙을 중복시킬 수 있어 채택하지 않는다.
- [기존 review topology 회고](../../../notes/2026-08-09-review-unit-risk-boundary-gap.md)에 따라 전체 변경을 같은 불변식을 공유하는 review slice 하나로 다룬다. 행동 시나리오 실행은 규칙의 검증이며 task별 코드 리뷰가 아니다.
- 반대 가정: 기존 모델이 이미 바르게 판단할 수 있다. baseline이 통과한 사례를 실패로 포장하거나 이번 변경으로 준수율이 개선됐다고 주장하지 않는다.

## 수용 기준

1. 주요 기능의 성공·실패·중요 경계를 구현 전에 관찰 가능한 시나리오와 검증 방법으로 구체화한다. 주요 기능의 핵심 시나리오와 검증 범위를 사용자와 검토한다. 이미 합의했거나 명시적으로 위임된 범위는 반복 확인하지 않는다.
2. 기대값은 현행 명세와 합의에서 도출한다. 과거 기록과 현재 정책을 구분하고, 구현 출력을 정답으로 재사용하지 않는다.
3. 실제 동작·영속성·렌더링에 필요한 증거를 선택한다. build, mock 테스트, AI 리뷰의 통과 범위를 확대 해석하지 않는다.
4. 실패를 없애려고 assertion·snapshot·skip을 임의로 완화하지 않는다. 합의된 요구 변경이나 동작 의미를 보존하는 테스트 정리는 진행한다.
5. 결함을 잡지 못하는 테스트를 검증 완료로 인정하지 않는다. 중요한 회귀는 알려진 결함에서 실패하는지 확인한다.
6. 통과·실패·미실행과 환경 차단 이유를 구분하고, 명령·조건·기대/실제·필요한 증거를 재현 가능하게 남긴다.
7. 주요 기능의 시나리오 검토는 구현 전에 묶어서 수행한다. phase별·케이스별 재승인, 모든 작업의 TDD/E2E 강제, task별 reviewer를 추가하지 않는다.

## 검증 방법

- 동일한 S1–S8을 변경 전후의 별도 에이전트에 제공한다. 제품 실행 결과는 주어진 사실로 한정하고, 모델이 실제로 수행하지 않은 결과를 만들지 못하게 한다.

- 이 검증은 문장 기반 행동 표본이다. 실제 제품 개발이나 여러 모델의 장기 준수율을 검증한 것은 아니다.
- 변경한 skill의 frontmatter와 로컬 링크, `AGENTS.md`/`CLAUDE.md`의 동일성, `git diff --check`를 검사한다.

## 위험 / 폐기 조건

- 위험: 일반적인 테스트 지침을 과도하게 늘려 작은 변경마다 긴 문서·승인·E2E를 요구할 수 있다.
- 폐기 조건: 합의·위임된 시나리오나 승인된 테스트 삭제가 재승인으로 막히거나, 미검토한 주요 시나리오를 AI 판단만으로 건너뛰거나, 검증 증거와 추가 리뷰 사다리가 다시 혼동된다.
- 대응: 작은 작업은 기존 계획·테스트 안에서 축약하고 시나리오/증거를 기존 문서와 연결한다. 주요 기능의 미검토 수용 범위는 함께 검토하고 기존 합의·명시적 위임을 재사용한다.

## 테스트 배경 주석 형식 보강

사용자와 합의한 `[테스트 배경]` 제목의 블록 주석을 검증 참조에 추가했다. 짧은 제목, 배경과 결정 이유, 확인한 근거 순서로 읽도록 예시를 제공한다.

- 테스트 이름·코드만으로 알기 어려운 맥락이 있을 때 사용한다. 자명한 테스트에는 주석을 강제하지 않으며 한 줄로 충분한 경우는 축약한다.
- 같은 배경은 테스트 묶음 위에 한 번만 작성한다. 확인되지 않은 과거 사건·이슈·링크를 만들지 않고, 상세 이력은 원문에 둔다.
- 요구가 바뀌면 구현·테스트·주석과 근거를 함께 갱신한다. 오래된 주석을 현행 합의보다 우선하지 않는다.
- 기존 간결한 주석 규칙과 behavior skill의 요약을 연결해, 필요한 배경을 기계적으로 한두 줄로 축약하지 않도록 했다. plan의 상세 가이드 진입 문구와 USAGE의 Y 시나리오도 맞췄다.

### 주석 보강 검증 결과

## 사례별 고정 분류를 공통 판단 기준으로 교체

라우팅 외에도 속성별 테스트 계층 표, 핵심 여정의 E2E 고정, 문자열·클래스 검사, UI 중심 책임·mock 설명, 예시의 입력 보존 정책을 점검했다. 공통 규칙은 `보호할 계약 → 관찰할 결과 → 필요한 실제 의존성 → 검증 방법`으로 정리했다.

- `verification.md`: 프로필 정책과 검증 계층을 결합한 표를 일반 시나리오 정보 구조로 교체했다. 속성별 계층 표와 라우팅·특정 React Router API 섹션은 계약·의존성의 판단 절차로 통합했다.
- `verification.md`: 실제 실행·렌더링 증거를 요구하는 원칙은 유지하면서 제품 환경과 현행 조건에서 도구를 고르도록 했다. assertion 문법·값의 타입·정적 검사 여부와 실제 검증 의미를 구분한다. 충분한 기존 증거를 재사용하되 단위 검사들을 전체 연결의 증거로 합산하지 않는다.
- `cadence-plan`, `using-cadence`, README: 같은 일반 원칙으로 진입 문구·설계 점검·요약과 참조 링크를 맞췄다.
- USAGE: 사례의 기능명·수치·도구를 매칭 조건으로 검사하지 않도록 평가 기준을 명시했다. 같은 검사 형태의 다른 계약, 같은 기능명의 다른 수용 범위, CLI·네이티브·미정 정책 사례로 판단 근거를 비교하도록 바꿨다.
- `[테스트 배경]` 형식과 공동 시나리오 검토는 유지했다. 주석의 예시 정책을 다른 기능의 요구로 가져오지 않도록 명시했다.

특정 제품 API의 설명을 공통 가이드에서 제거했으며, 실제 프로젝트에서 사용할 버전·설정·명령은 프로젝트/stack 가이드에서 확인하도록 했다. 별도의 프로젝트 구현이나 도구 설정을 새로 만든 것은 아니다. 앞선 단계의 라우팅 표·평가 기록은 당시 작업 이력이며 현행 규칙으로 재사용하지 않는다.

### 일반화 보강의 검증 결과

G1–G6의 판단 응답을 변경 전후 독립 에이전트에서 받아 사전 기준으로 평가했다. 변경 전에도 계약에 따라 타당한 방법을 골랐으며, 변경 후에도 여섯 상황에서 필요한 실제 증거와 미합의 정책 검토 경계를 보존했다. 이는 문장 응답 평가이며 특정 문자열 존재를 검사한 테스트가 아니다. 실제 제품 실행이나 일반적인 성능 개선을 입증하지 않는다.

문서의 링크·앵커, skill 3개의 형식, root mirror와 `git diff --check`는 통과했다. 누적 변경 문서 10개의 로컬 링크 77개를 확인했다. 로컬 문서 수정 상태다.
