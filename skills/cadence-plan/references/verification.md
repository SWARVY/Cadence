# 수용 시나리오와 검증 증거

주요 기능의 시나리오를 정하거나, 테스트를 변경하거나, 완료 근거가 부족할 때 읽는다. 사용자 게이트는 [using-cadence](../../using-cadence/SKILL.md)가 소유한다. 세부 테스트마다 추가 승인을 요구하거나 특정 테스트 도구를 강제하지 않는다.

이 문서는 기능별 정답표가 아니라 판단 기준이다. 기능명·라이브러리·assertion 문법만으로 테스트 방법이나 유용성을 결정하지 않는다. 예시는 명시된 조건에서 원칙을 설명하며, 예시의 제품 정책·수치·도구를 현재 요구로 가져오지 않는다.

## 구현 전에 기대 동작을 정한다

주요 기능은 구현 전에 핵심 수용 시나리오를 사용자와 함께 검토한다. AI의 명확성 판단만으로 시나리오의 충분함이 합의되지는 않는다.

1. AI가 기획·현행 계약·관련 결정에서 핵심 시나리오와 검증 범위의 초안을 만든다. 확인한 요구, 추정한 내용, 남은 질문을 구분한다.
2. 사용자에게 조건·행동·기대 결과를 보여주고 빠진 중요한 상황과 수용 범위를 묶어서 검토한다. 초안 없이 진행 승인만 묻거나 케이스마다 따로 승인받지 않는다.
3. 합의된 범위에서 AI가 세부 경계값·테스트·구현을 구체화한다. 기대 동작이나 수용 범위가 달라지면 해당 변경을 다시 논의한다.

이미 해당 핵심 시나리오와 범위를 함께 합의했거나 사용자가 선정·상세화를 명시적으로 위임했다면 반복 확인 없이 진행한다. 기존 합의된 명세에 같은 내용이 있으면 그 기록을 재사용한다. 일반적인 “구현해줘”만으로 시나리오 검토까지 위임받았다고 해석하지 않는다. 작은 수정에는 이 검토를 일괄 적용하지 않으며 구체적인 경계는 [using-cadence §1-8](../../using-cadence/SKILL.md#1-8-수용-기준과-검증-경계)을 따른다.

- 코드와 기존 테스트는 현재 동작을 설명하는 자료다. 기대 동작과 그 이유는 현행 명세·합의에서 확인한다. 과거 회의록·PR·주석은 당시 맥락이며, 지금도 유효한지 확인한다.
- 자료가 충돌하면 최신 날짜만으로 결정하지 말고 적용 범위와 대체된 결정인지 확인한다. 확인된 요구, 작업 가정, 미해결 결정을 구분한다.
- 중요한 이유와 출처를 기존 spec·issue·결정 기록에 연결한다. 코드에서 알 수 없는 정책을 추측하거나 회의록 전체를 테스트 주석에 복사하지 않는다.
- 주요 흐름의 정상 경로, 실패·복구, 중요한 경계를 고른다. 모든 조합을 나열하지 않고 누락의 영향과 발생 가능성에 비례한다.

기존 계획이나 테스트에 다음 정보를 연결하면 충분하다. 별도 문서나 특정 Given/When/Then 문법은 필수가 아니다.

| 시나리오 | 근거 / 이유 | 조건·행동 | 관찰할 결과 | 검증 방법 / 경계 |
| --- | --- | --- | --- | --- |
| <보호할 요구> | <현행 계약·합의와 이유> | <초기 상태와 수행할 행동> | <독립적으로 정한 기대 결과> | <필요한 실제 의존성·통제할 경계·확인 방법> |

시나리오를 테스트 이름/식별자와 연결하면 실패 시 어떤 요구가 깨졌는지 찾을 수 있다. 단순 수정은 짧은 설명과 기존 테스트로 축약한다. 적용 사례는 [USAGE의 검증 시나리오](../../../USAGE.md#p-구현-전에-시나리오-구체화)에 두며, 사례에 없는 정책을 추측해 기대값으로 채우지 않는다.

## 검증 경계와 의존성을 정한다

테스트 개수나 코드 커버리지 자체를 완료 기준으로 삼지 않는다. **보호할 계약 → 관찰할 결과 → 필요한 실제 의존성 → 검증 방법** 순서로 판단한다.

1. **계약과 결함을 정한다.** 현재 수용 조건과 그 조건을 어기는 대표 오동작을 확인한다. 구현의 출력이나 예시를 그대로 정답으로 삼지 않는다.
2. **필요한 연결을 찾는다.** 관찰할 결과가 어느 구성 요소의 계산·상호작용·실행 환경에 달려 있는지 확인한다. 단일 단위의 공개 출력으로 충분한지, 여러 구성 요소의 실제 연결이나 프로세스·장치 등 실행 환경까지 포함해야 하는지 판단한다.
3. **대체 가능한 경계를 구분한다.** mock이 보호하려는 동작이나 연결 자체를 대신하면 해당 동작의 증거가 되지 않는다. 수용 범위 밖의 의존성은 조건을 통제하기 위해 대체할 수 있으나, 대체한 부분의 실제 동작까지 확인했다고 하지 않는다.
4. **기존 증거를 대조한다.** 기존 검증이 같은 계약·조건·변경된 연결을 확인하는지 검토하고 충분하면 재사용한다. 개별 단위가 통과했다는 사실만으로 그 사이의 연결까지 검증됐다고 합산하지 않는다.
5. **충분한 방법 중 비용이 적은 것을 선택한다.** 프로젝트에서 지원하는 방법 중 필요한 동작을 실제로 관찰하고 결함을 검출할 수 있으며 실행·유지보수 비용이 적은 경계를 고른다. 유닛·통합·E2E 등의 명칭이나 기능 종류가 선택 근거를 대신하지 않는다.

하나의 수용 조건에 여러 증거가 필요할 수 있다. 여러 구성 요소가 이어지는 여정도 필요한 연결이 실제로 검증됐는지 확인하고, 기존 증거로 부족한 경계만 추가한다. 세부 조합을 더 좁은 테스트로 나눌 수 있지만 그 과정에서 연결 검증을 빠뜨리지 않는다. 모든 여정을 같은 계층으로 고정하거나 충분한 검증을 중복하지 않는다.

라이브러리와의 연결이 계약에 포함되면 우리 설정·호출·데이터가 실제 라이브러리와 함께 동작하는지 확인한다. 지원되는 테스트 컨텍스트가 필요한 연결을 포함하는지 먼저 살피고, 검증 범위 밖의 라이브러리 내부 동작까지 재시험하지 않는다. 구체적인 API·설정·fixture·명령은 프로젝트나 stack 가이드에서 사용 버전과 실행 모드에 맞춰 확인한다.

선택 결과는 기존 계획에 `시나리오 / 방법을 선택한 이유 / 실제·대체 의존성 / 테스트 위치와 실행 방법 / 남은 확인`으로 연결한다. 더 넓은 검증이 필요하면 좁은 테스트로 부족한 부분을 설명하고 해당 시나리오를 적절한 위치에 추가한다. 환경이 없으면 필요한 확인을 미실행으로 남기며 대체한 경계의 테스트로 완료 처리하지 않는다.

## 실행 환경에서 관찰해야 하는 결과

수용 조건이 실제 실행 환경에서 드러나는 결과에 관한 것이면, 그 결과가 발생하는 환경에서 증거를 얻는다. 설정·소스·선언된 값이 있다는 검사만으로 실제 실행 결과까지 확인했다고 하지 않는다. 반대로 선언된 출력 자체가 계약이면 그 검사는 해당 계약의 증거로 사용할 수 있다.

실제 시각 상태나 인터랙션이 요구라면 해당 제품의 렌더링·조작 환경에서 확인한다. 웹·네이티브 등 환경에 맞는 기존 도구를 선택하고, 재현에 필요한 비교 기준·환경 설정·데이터·상태·조작 순서를 기록한다. 화면 크기·배율·입력 방식 같은 조건은 현행 요구에서 선택하며 특정 예시의 값이나 브라우저 도구를 모든 제품에 강제하지 않는다. 필요한 이미지·실행 기록을 남기고 한 번의 관찰과 반복 실행 가능한 검증을 구분한다.

build와 AI 리뷰가 통과해도 수용 조건에 필요한 실제 관찰을 대신하지 않는다. 비교 허용치를 넓히거나 검증 범위를 줄여 통과시키려면 기대 결과 변경으로 검토한다.

## 의미 있는 assertion 선택

각 테스트가 **어떤 요구를 보호하고, 어떤 오동작에서 실패해야 하는지** 설명할 수 있어야 한다. assertion의 문법·값의 타입·정적 또는 동적 검사 여부만으로 유용성을 판정하지 않는다.

- 관찰값과 기대값이 현행 계약에 어떻게 연결되는지 확인한다. 구현 세부사항만 바뀌었는데 실패하는 검사인지, 필요한 동작을 제거해도 통과하는 검사인지 검토한다.
- 필요한 동작의 결함을 놓치는 검사는 그 동작의 완료 근거로 삼지 않는다. 승인 범위에서 제거·교체하거나 부족한 증거를 보강하되, 기존 검증이 충분하면 중복을 피한다.
- 문자열·구조·호출 인자·횟수 등도 그 자체가 명시된 계약이면 검증한다. 특정 함수명·클래스명·비교 연산자만으로 검사를 일괄 유지하거나 삭제하지 않는다. 공개된 계약인지는 현행 요구에서 확인한다.
- 보호할 계약과 무관한 내부 구조·구현 순서에 결합하지 않는다. 출력 계약의 통과를 그 출력을 사용하는 전체 시스템의 동작 증거로 확대하지 않는다.

[적용 예시](../../../USAGE.md#v-의미-있는-assertion과-검증-공백)는 같은 검사 형태도 계약에 따라 의미가 달라짐을 보여준다. 예시의 문자열을 금지 목록이나 검사 도구의 매칭 조건으로 사용하지 않는다.

## 책임 분리와 mock 판단

[구현 전 테스트 가능성 점검](../SKILL.md#구현-전-테스트-가능성-점검)을 설계 때 적용한다. 관찰할 동작, 입력·출력, 상태 소유권과 부작용을 확인하고 독립적인 변경 이유가 한곳에 얽혀 있는지 검토한다.

mock이 많거나 설정이 복잡한 것은 조사 신호다. 책임 집중 때문인지, 실제 협력 모듈을 포함해야 할 테스트를 지나치게 고립시켰는지, 수용 범위 밖 의존성을 정당하게 통제하는 것인지 구분한다. 개수나 의존성 종류만으로 구조를 판정하지 않는다. 검증 대상의 내부 판단을 mock에 복사하면 그 판단의 결함을 검출할 수 있는지 다시 확인한다.

기존 공개 입출력과 동작으로 충분히 검증할 수 있으면 구조를 유지한다. 분리는 독립적인 책임·변경 이유·부작용 경계가 있을 때 선택하고, 테스트 편의를 위한 불필요한 계층·공개 API·의존성 주입을 만들지 않는다. 기존 API·아키텍처 변경이 필요한 경우에는 승인 범위를 확인한다.

## AI가 수정해도 의미가 유지되는 테스트

- 테스트 이름은 시나리오와 실패한 약속을 드러내고, 입력·기대값·행동은 읽을 수 있게 둔다. 실패 메시지는 기대/실제의 차이를 보여준다.
- 기대값을 테스트 대상 함수로 계산하거나 구현의 분기식을 복사하지 않는다. 잘못된 구현을 함께 정답으로 만드는 fixture·mock도 피한다.
- 관찰할 출력·상태·상호작용은 공개 계약을 기준으로 고른다. 검증 범위와 무관한 내부 구조에 결합하지 않되, 명시된 구조나 값 자체가 계약이면 그 결과도 검증한다.
- 시간·랜덤·데이터·네트워크는 재현 가능한 조건으로 제어하고 테스트 간 상태를 격리한다. 통제한 의존성과 실제로 확인하지 못한 경계를 명시한다.
- 버그 수정에서는 재현 테스트가 기존 결함 때문에 실패하고 수정 후 통과하는지 확인한다. 환경 오류를 RED 증거로 삼지 않는다. 중요한 신규 테스트도 대표 오동작을 넣었을 때 검출하는지 확인할 수 있다. 모든 테스트에 mutation testing을 강제하지 않는다.
- 알려진 결함을 넣어도 통과하면 테스트가 놓친 경계를 보강한다. AI가 작성한 구현과 테스트가 서로 동의한다는 사실만으로 닫지 않는다.

### 테스트 배경 주석

테스트 이름은 조건과 기대 결과를, 주석은 이름과 코드만으로 알기 어려운 배경·결정 이유·검증 경계를 설명한다. 이런 맥락이 필요할 때 테스트 위에 **짧은 제목 → 배경과 결정 이유 → 확인한 근거** 순서의 블록 주석을 권장한다. 제목은 `[테스트 배경]`을 사용한다.

아래는 입력값 유실 버그와 입력 보존 결정이 확인됐다고 가정한 형식 예시다. 다른 기능의 실패 정책으로 가져오지 않는다. 실제 적용할 때는 해당 기능에서 확인한 배경과 근거를 사용한다.

```ts
/*
 * [테스트 배경] 저장 실패 시 입력 보존
 *
 * 오류 처리 과정에서 폼을 초기화해 사용자가 내용을 다시 작성해야 했다.
 * 재입력 없이 저장을 재시도할 수 있도록, 실패 시 입력을 보존하기로 했다.
 *
 * 근거: <관련 이슈 또는 결정 문서 링크>
 */
test('저장 실패 시 입력값을 유지한다', async () => {
  // 테스트 구현
});
```

- 모든 테스트에 이 양식을 강제하지 않는다. 자명한 내용은 생략하고, 필요한 맥락이 짧으면 한 줄로 충분하다. 형식을 채우려고 테스트 이름·구현 절차를 반복하지 않는다.
- 여러 테스트가 같은 배경을 공유하면 관련 `describe` 등 테스트 묶음 위에 한 번만 작성한다.
- 확인한 히스토리만 적는다. 과거 사건이 없으면 필요한 현재 요구의 이유만 설명한다. 출처가 없으면 근거 항목을 생략하며, 이슈 번호·링크·과거 장애를 추측해 만들거나 미완성 자리표시자를 남기지 않는다.
- 상세 이력은 원문에 두고 핵심 맥락만 요약한다. 요구가 바뀌면 구현·테스트·주석과 근거를 함께 갱신한다. 오래된 주석을 현행 합의보다 우선하거나 변경 연대기를 계속 덧붙이지 않는다.

### 기대 결과를 바꾸려 할 때

실패를 없애기 위한 assertion 삭제, expected/snapshot 갱신, skip, 이미지 허용치 확대는 수정의 근거가 아니다. 먼저 현행 요구와 실패 원인을 대조한다.

| 상황 | 처리 |
| --- | --- |
| 구현이 합의된 요구를 어김 | 요구를 보존하는 테스트를 유지하고 구현 수정 |
| 사용자가 요구 변경을 이미 승인함 | 구현·테스트를 함께 갱신하고 바뀐 근거 연결. 같은 승인 반복 금지 |
| selector/구조 변경, 중복 또는 무의미한 테스트 정리 | 검증 의미와 필요한 커버리지를 보존하며 승인 범위에서 수정·삭제 |
| 새 제품 정책·공개 계약 선택이 필요함 | 충돌·영향·추천을 보고하고 해당 결정 전 정지 |

불안정한 테스트도 우선 원인을 진단한다. 격리가 필요하면 확인하지 못하는 범위·대체 증거·복구 작업을 명시하고 프로젝트 정책을 따른다. 격리로 사라진 검증을 통과로 보고하지 않는다.

## 실행 결과를 다음 수정에 쓸 수 있게 남긴다

필요한 증거는 기존 테스트 출력·CI·issue·계획에 연결한다. 모든 로그를 최종 답변에 복사하거나 매 작업에 새 보고서를 만들 필요는 없다.

```text
시나리오 / 깨진 요구:
실행한 변경 버전과 환경 / 실제로 사용한 의존성·mock 경계:
실행 명령 또는 조작 순서 / 재현 데이터:
기대 결과 → 실제 결과:
상태: 통과 | 실패 | 미실행 (환경 차단 등 이유)
관련 로그·screenshot·trace / 남은 확인:
```

시작조차 못 한 테스트와 assertion 실패를 구분한다. 환경이 막히면 승인 범위 안에서 원인을 진단하고 독립적으로 가능한 검증은 이어가며, 부족한 증거를 통과로 바꾸지 않는다. 필요한 수용 조건이 미확인이면 구현된 범위와 검증 완료를 구분하고 그 조건까지 완료했다고 보고하지 않는다.

완료 보고에는 수용 조건별 결과를 요약하고, 실패가 있다면 원인·다음 조치, 미실행이면 이유·남은 확인을 남긴다. 합의한 접근을 바꾸는 결정이나 승인 범위 밖의 조치가 필요할 때만 [using-cadence](../../using-cadence/SKILL.md)의 게이트로 돌아간다.
