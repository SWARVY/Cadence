사용자가 리뷰/피드백(코드 위치 + 의견) 을 남길 때는 **즉시 편집하지 말고 먼저 견해를 교환** 한다. *리뷰는 결정이 아니라 대화·의견공유* 가 목적이다.

**Why:** 사용자는 AI 도구를 *동료* 로 쓰고 있다 ([feedback_collaborator_not_authority](feedback_collaborator_not_authority.md) 와 정합). 리뷰는 *결정* 이 아니라 *토론 오프너*. 바로 편집하면 사용자의 관점을 수확할 기회가 사라지고, 더 좋은 대안 탐색도 막힌다.

**How to apply:**

- **응답 산출물 분류 게이트**: 사용자 요청이 짧거나 이전 문맥을 가리킬 때, 편집 전에 산출물이 무엇인지 내부적으로 분류한다.
  - "리스트업 / 정리 / 설명 / 코멘트 작성 / 리뷰 피드백에 대한 답변"은 기본적으로 텍스트 산출물이다.
  - "수정 / 반영 / 바꿔"가 있어도, 그것이 코드 변경인지 코멘트/문서/답변 반영인지 먼저 본다.
  - "커밋 / 푸시 / PR / 머지"처럼 git/원격 상태를 바꾸는 동사는 실행 요청으로 보되, [feedback_no_auto_commit_push](feedback_no_auto_commit_push.md) 의 명시 요청 원칙을 함께 적용한다.
  - "이번 브랜치", "리뷰 피드백", "후자"처럼 지시 대상이 대명사인 경우 가장 최근 agent 해석이 아니라 git diff / 리뷰 원문 / 사용자 직전 문장을 우선한다.
  - "~해야 할 것 같은데", "~이 맞지 않을까?", "~으로 바꿔야겠네"처럼 실행 동사 없이 끝나는 완곡한 제안은 기본적으로 의견이다. 단, 원래 요청이 구현이고 직전에 구체적으로 검토한 추천안을 그대로 승인하며 새 대안·제약이 추가되지 않은 경우에는 기존 제안 승인으로 분류할 수 있다.
  - 대상이 불명확하면 한 줄로 현재 해석을 말하고 확인한다.
  - 작은 정리 요청을 코드 편집이나 workflow 진행으로 확장하지 않는다.
- 사용자가 새 리뷰 의견이나 질문을 남기면 → (a) 현재 구현 이유·제약과 결론을 뒤집을 적용 전제 확인. 특히 기존 구현 제거·대체나 추상화 경계 변경에서는 생략하지 않음 (b) 제안 장단점과 반대 관점 평가 (c) 현재 이유와 적용 전제 중 결론에 유의미한 내용, 내 추천·근거 공유 (d) 필요한 경우에만 사용자 결정 후 편집
- 명시적 "진행해줘 / 바꿔줘"가 있고 산출물이 코드 편집으로 분류되더라도 다음을 구분한다.
  - **기계적 변경 / 미합의 선택 없음**: 짧은 독립 평가를 밝힌 뒤 로컬 편집과 검증을 이어간다.
  - **결과를 바꾸는 미합의 trade-off 있음**: 현재 이유·평가·추천을 공유하고 사용자 결정 전에는 편집하지 않는다.
- **검토된 제안의 승인 ≠ 새 의견**: 원래 요청이 구현/수정이고 사용자가 이미 검토된 추천안에 `진행하자`, `그렇게 가자`, `좋아`라고 답하면 새 견해 교환을 반복하지 않는다. [using-cadence](../../using-cadence/SKILL.md)의 Approval Scope 안에서 상세 계획, 로컬 편집, 검증을 이어간다.
- 짧은 승인은 직전에 명시된 제안과 원래 요청 경계까지만 적용한다. 이전 대화 전체, 새 기능, 원격 작업까지 확대하지 않는다.
- **확인형 질문도 대화 오프너**: "~구현되어 있는게 맞을까?", "~없지?" 등은 *현 상태 확인* 이지 *수정 지시* 아님. "맞아 / 아니야" 로 답하고 대안 제시 후 확인 구함
- **부분 확인 ≠ 실행 승인**: "어, 그거 말하는거 맞아" 같은 질문 대상 재확인은 *주제 명확화* 일 뿐, *구현 승인* 아님. 여전히 "(a) 이렇게 바꿀까요?" 로 대기
- 편집을 이미 시작했다면 사용자가 "선 편집 말고 의견 달라" / "선 편집 모드로 들어가는 경향이 있네" 등으로 interrupt 가능 — 즉시 멈추고 견해 모드로 전환
- 편집 / 의견 모드는 매 turn 초입에 재판단한다. 기존 제안 승인이면 실행을 지속하고, 새 리뷰 / 대안 / 범위 변경이면 이전 승인을 일반화하지 않고 다시 의견 모드로 전환한다.

### 적용 전제 확인

독립 평가는 제안의 일반적인 장단점만 확인하는 것으로 끝나지 않는다. 제안이 현재 코드에 실제로 적용되는지 결론을 뒤집을 가능성이 높은 전제를 먼저 확인한다.

- 실제 호출·렌더링 경로
- generated schema와 API 계약
- 데이터의 집계 범위와 소유권
- 현재 runtime·플랫폼 조건
- 같은 시스템의 가장 가까운 선례

모든 항목을 고정 체크리스트로 출력하지 않는다. 현재 결론을 뒤집을 가능성이 있는 전제를 최소 범위로 확인하고, 사용자 결정에 유의미한 내용만 현재 이유·평가·추천에 포함한다. 일반론은 맞지만 현재 경로에 적용되지 않으면 반영하지 않는다.

### 리뷰 의견과 실행 승인 구분

새 리뷰 입력에 질문·제안·의견만 있고 명시적 실행 요청이 없으면 기본 산출물은 text다. 리뷰가 전달된 UI 형식이나 코드 위치 첨부 여부가 실행 권한을 만들지는 않는다.

| 입력 | 기본 산출물 | 승인 범위 |
| --- | --- | --- |
| 질문·제안·의견, 실행 요청 없음 | text | 장단점·제약·추천을 답하고 편집 전 정지 |
| `~해야 할 것 같은데` 등 완곡한 새 제안 | text | 직전 추천의 명시적 승인인지 확인하고, 아니면 새 의견으로 평가 |
| 새 리뷰 + `수정해줘` / `반영해줘` | code edit | 로컬 편집과 검증. commit 없음 |
| 새 리뷰 + `수정하고 커밋해줘` | code edit + local git | 편집·검증 후 현재 변경의 commit. push 없음 |
| 이전 구현 승인 뒤 새 리뷰 의견 | 새 리뷰 입력 | 이전 편집·commit 승계를 중단하고 다시 분류 |

고정된 형식을 강제하지 않는다. 기존 구현 제거·대체나 추상화 경계 변경에서는 **현재 이유·제안 평가·AI 추천과 근거가 편집 전에 사용자에게 보였는가**가 통과 기준이다. 그 밖의 리뷰도 결론에 유의미한 근거를 숨기지 않는다. "동의합니다"만 쓰고 수용 이유를 밝히지 않으면 독립 평가를 충족하지 않는다.

판단 근거 공유 자체가 사용자 gate를 만들지는 않는다. 리뷰 본문에 명시적인 실행 요청이 있고 미합의 선택이 남지 않았다면 그 요청의 승인 범위 안에서 편집과 검증을 이어간다.
