코드 작성 / typecheck / lint가 끝났더라도 **커밋과 원격 반영 (push / PR 생성·업데이트·close / merge / branch 삭제 / force-push / 이슈·PR 댓글 등 모든 원격 영향 행위)은 사용자가 명시적으로 요청할 때만** 진행한다. 단, terminal intent가 명확한 요청은 그 목적을 달성하는 필수 선행 단계를 포함한다.

**Why:** AI 가 일련의 워크플로우 끝에서 *자연스럽게 커밋·푸시까지 이어가는* 흐름은 사용자 검토 단계를 우회해 *원격 저장소에 미검증 변경이 올라가는* 결과로 이어진다. 도구별 root config 에서 흔히 두는 "명시 요청 시에만 commit/push" 규칙과 같은 맥락이다.

**How to apply:**

1. 로컬 구현과 검증만 요청받았으면 변경 파일 + 검증 상태를 보고하고 멈춘다.
2. 요청 동사와 terminal intent로 승인 범위를 정한다.
3. 명시적으로 승인된 외부 단계는 경계를 보고하되, 다음 단계가 같은 승인 범위에 있으면 허가를 반복해서 묻지 않는다.
4. 승인 범위 밖의 외부 단계 앞에서만 보고 후 정지한다.

### Terminal action preflight (mandatory)

commit / push / PR / merge / 댓글 / 배포처럼 보호되는 Git·외부 상태 변경 직전에 다음을 내부적으로 모두 확인한다.

1. **Terminal intent**: 현재 turn 또는 아직 진행 중인 명시적 연속 지시에 지금 수행할 행동이 포함되어 있다.
2. **변경 사이클**: 그 승인이 지금 바꾸려는 상태와 diff에 적용되며, 이전 변경의 승인을 새 리뷰·후속 수정에 재사용하지 않았다.
3. **리뷰 산출물**: 현재 입력이 질문·제안·의견만 있는 review-only 요청이거나 별도 실행 요청이 빈 상태가 아니다.
4. **Branch policy**: Git 상태를 바꾸는 작업이면 현재 branch를 확인했고 프로젝트의 `main` / `master` 직접 commit·push 정책에 어긋나지 않는다.
5. **권한 출처**: 권한은 사용자 terminal intent에서 왔으며, 하위 workflow skill의 단계나 테스트·build·formatter 완료에서 추론하지 않았다.

하나라도 충족하지 않거나 불명확하면 해당 행동을 수행하지 않고 로컬 변경과 검증 상태만 보고한다. commit은 원격 작업은 아니지만 사용자가 명시적으로 통제하는 Git 상태 변경이다.

### 상태 변경 postcondition (mandatory)

보호된 행동을 수행한 뒤에는 사용자에게 보고하기 전에 실제 도구 결과와 현재 상태를 확인한다.

1. 성공한 행동만 완료로 보고한다. 실패·중단·생략한 행동에는 완료 문구나 상태 신호를 붙이지 않는다.
2. **행동 종류를 보존한다.** branch 전환은 branch 생성이 아니고, fetch·pull은 merge나 설치가 아니며, staging은 commit이 아니다.
3. commit hash, 원격 동기화 상태, PR URL처럼 결과를 식별할 수 있는 증거가 있으면 실제 값과 대조한다.
4. 현재 변경 사이클에서 발생하지 않은 과거 상태를 새로 수행한 것처럼 보고하지 않는다.

preflight는 권한을 증명하고 postcondition은 실행 사실을 증명한다. 둘 중 하나만 통과해서는 사용자에게 상태 변경 완료를 주장할 수 없다.

| 요청 | 승인 범위 |
| --- | --- |
| "커밋해줘" | 현재 합의된 변경의 commit. push 없음 |
| "푸시해줘" | 이미 commit된 현재 변경의 push. uncommitted 변경의 새 commit은 별도 확인 |
| "PR 올려줘" | 최신 검증, 필요한 branch / commit, push, PR 생성. merge 없음 |
| "머지해줘" | 지정되거나 현재 합의된 PR merge. main sync / branch 삭제 / 설치본 갱신 없음 |
| 명시적 연속 지시 | 열거된 외부 단계 전체 |

**Edge cases:**

- 사용자가 PR 리뷰 코멘트를 붙여넣으며 "반영" 만 요청하면 — 코드 수정 + 검증까지만, 커밋·푸시는 추가 요청 대기.
- "릴리즈해줘" / "배포해줘" 처럼 흐름 전체가 명시되면 — 그 안에 푸시까지 포함된 것으로 간주.
- `PR 올려줘` 실행 중 commit 완료 보고는 checkpoint다. push와 PR 생성이 이미 승인됐으면 다시 묻지 않는다.
- **한 PR 사이클 안에서 한 번 "커밋 푸시 해줘"를 받았다고 그 후속 변경까지 자동 푸시하지 말 것** — 새 변경에는 새 명시 요청이 필요하다.
- 새 PR 사이클 / 새 브랜치 시작 시에는 자동으로 권한 계승되지 않음. 다시 명시 요청 받음.
- PR 생성 또는 merge로 요청된 terminal intent가 끝나면 해당 변경 사이클의 commit / push 권한도 만료된다. 이후 새 리뷰·수정은 새 요청으로 분류한다.
- "PR 올리고 머지한 뒤 설치본도 업데이트"처럼 후속 단계까지 열거된 연속 지시만 해당 단계까지 권한을 유지한다.
